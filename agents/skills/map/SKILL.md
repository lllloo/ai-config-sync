# map

把專案的**關係與約束**畫成可閱讀的圖，不把檔案樹改畫成方框。預設給工程師；使用者點名經理、新同事等讀者時，只調整標籤與旁註的詞彙、深度和切入點，不改變節點、箭頭或證據。

## 快速流程

1. **定範圍與問題**：用一句話固定這張圖要回答的問題，例如「CLI 執行時如何走到各功能模組？」。無參數時畫整體；路徑或子系統時只畫該範圍。範圍不明且會改變圖型時，列 2–3 個具體選項請使用者選，不問空泛問題。
2. **取證，不猜測**：先讀相關 `AGENTS.md`、`CLAUDE.md`、`README.md`；再快速查實際 import／require、呼叫、讀寫與設定。文件是骨架、程式碼是關係依據。找不到依據就列為「未納入」，不要補畫一條看似合理的線。
3. **先排頁，再繪圖**：內容多時絕不縮字或塞進一張。全專案預設做「總覽」與「核心路徑」兩頁；只有某個問題不能由這兩頁回答時，才加 1–2 張聚焦頁。小於 5 個互相關聯節點的小範圍可只做一頁。每頁只回答一個問題。
4. **寫 brief 後製圖**：依 [圖面 brief 與 rendering contract](references/diagram-brief.md) 整理節點、邊、證據與省略項；再以原生 HTML/CSS/inline SVG 製成單一檔案。不要等待或依賴另一個 skill、CDN、圖形函式庫或建置步驟。
5. **反證後交付**：依下方品質閘檢查；不通過就拆頁、刪除無關節點或補查證據，不能靠縮放修飾。交付時附可點連結、範圍與未畫內容。

## 頁面與圖型

- **總覽頁**：用 architecture／dependency 圖說明外部邊界、主要分層與誰依賴誰。6–12 個節點、最多 14 條邊；分層或 trust boundary 必須以區塊表示。
- **核心路徑頁**：用 sequence 或 data-flow 圖講一條從起點到終點的真實路徑；函式庫或純工具專案則改畫最常用 API 到結果的依賴路徑。
- **聚焦頁**：只在有獨立讀者問題時使用：模組內依賴、決策流程、狀態轉換或安全／資料邊界。不要為了湊頁數而重複總覽。

流程圖必須有明確起點與終點、固定的時間方向、主路徑編號（4–8 步）和每條箭頭的動作或資料標籤。判斷菱形的出口要寫條件；例外路徑若會交叉或超過兩條，移到另一頁，不畫成麵條圖。禁止或不得觸碰的關係以斷線、`禁止` 標籤與文字說明呈現，不能只靠顏色。

## 產物 contract

產出是完整、可離線開啟的單一 HTML：`<!doctype html>`、`lang="zh-Hant"`、UTF-8、viewport、inline CSS/JS 和 inline SVG。每頁是可切換的 tab／panel；初次開啟只顯示總覽，提供頁碼與上一頁／下一頁，鍵盤可操作。不要預設動畫、下載功能、搜尋、主題切換或任何不直接幫助理解關係的互動。

每張 SVG 要有 `<title>`／`<desc>`、`viewBox`、圖例與可讀的 14px 以上標籤；長中文標籤要換行或使用 `foreignObject`，不得溢出節點。窄螢幕保留字級並容許水平捲動，不把整張圖縮到看不清。以實線／虛線、箭頭、形狀和文字共同表達語意，顏色只作輔助。

一次性圖寫 scratchpad；使用者明確要納入版控時才寫 `docs/architecture/`。產生頁面後主動附絕對路徑與可點連結；WSL 使用 `file://wsl.localhost/<distro>/<絕對路徑>`。不要上傳或發佈產物。

## 反證式品質閘

交付前逐項反問：

1. 拿掉目錄名稱後，是否仍能看懂箭頭關係？否則它只是檔案清單。
2. 每一頁是否只回答一個讀者問題，且未超過節點／邊的密度上限？否則拆頁，不縮字。
3. 不看旁註，是否仍能從流程的方向、編號、起點、終點和分支條件走完主路徑？否則重排流程。
4. 每條關係是否有程式碼或明確文件依據？沒有就移到未納入項，不能推測。
5. HTML 是否無外部 runtime 且分頁、文字與 SVG 在靜態檢查上完整？否則先修好再交付。

## 不畫什麼

目錄樹、一對一來源／目的地對照與無關聯的孤立檔案改用文字或表格。整庫 ER 圖、部署圖與每個功能的細節不是預設產物；只有使用者指定問題且有足夠證據時才各自另畫聚焦頁。
